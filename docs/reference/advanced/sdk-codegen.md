# SDK Codegen — A Typed SDK Over the Entity Graph

<!-- last-reviewed: 2026-05-13 -->

`dogsled sdk generate` emits a project-local TypeScript SDK from the compiled entity graph. The generated files are meant to be checked into the consuming app repo, reviewed in Git, and regenerated whenever entity specs change.

The SDK is **executor-backed**: it owns typed filters, includes, and the query builder; the consumer owns warehouse / API / MCP execution through a single `find(request)` function.

## Read This If

- If you need app code or an agent tool with typed access to resolved entities, declared relationships, and document mentions.
- Require compile-time guarantees that callers cannot pass unsupported filter keys or unknown entity types.
- When setting up CI for an entity graph project with the SDK regen and type-check gate.

## Prerequisites

- A working entity graph project: specs in `entity-graph/`, `__entity_profile` materialized.
- Node ≥ 18 in the consuming app. The generated SDK targets `tsc >= 5.0 < 5.5`.

## What the Generator Does

```text
   entity-graph/*.yml           Compiled inventory          Generated SDK
┌──────────────────────┐    ┌──────────────────────┐   ┌─────────────────┐
│  customer.yml        │    │  inventoryEntityGraph│   │  entities/      │
│  deal.yml            ├───▶│   ()                 ├──▶│    customer.ts  │
│  document.yml        │    │  →  SDK IR (1.0)     │   │    deal.ts      │
│  mention_extraction  │    │      Zod-strict      │   │    _quality.ts  │
│   .yml               │    │                      │   │  runtime.ts     │
│                      │    │                      │   │  client.ts      │
└──────────────────────┘    └──────────────────────┘   │  index.ts       │
                                                       └─────────────────┘
```

`inventoryEntityGraph()` in `@bobsled-inc/entity-graph/api` is the bridge. It returns a typed snapshot of entities, relationships, profile attributes and dialect capabilities, which the code generator reads. You can call it directly from an agent or build script to inspect a project without spawning the CLI.

## Generate

```bash
dogsled sdk generate --lang ts --out ./generated/dogsled-sdk
```

| Flag                   | Use                                                          |
| ---------------------- | ------------------------------------------------------------ |
| `--lang ts`            | TypeScript output (the only language wired into the v1 CLI). |
| `--out <dir>`          | Output directory (default `./generated`).                    |
| `--integration <name>` | Build the IR against one configured integration handle.      |
| `--ir-only`            | Validate the inventory without writing files.                |
| `--json` / `--yaml`    | Emit a machine-readable manifest.                            |
| `--verbose`            | Include every emitted file in human output.                  |
| `--quiet`              | Suppress success output.                                     |

The Python emitter is available as a library export from `@bobsled-inc/sdk-codegen` for tooling that needs it, but it is not wired into the CLI yet. `--lang python` rejects with an actionable error.

## Generated Files

```text
generated/dogsled-sdk/
├── index.ts          # Re-exports everything below.
├── runtime.ts        # EntityFindRequest, EntityQueryBuilder, BobsledEntityExecutor.
├── client.ts         # createBobsledClient(executor) factory.
└── entities/
    ├── _quality.ts   # EntityQuality interface — imported by every entity.
    ├── customer.ts   # CustomerId + CustomerProfile.
    ├── document.ts   # DocumentId + DocumentProfile.
    └── deal.ts       # DealId + DealProfile.
```

The header of every file starts with a machine-readable codegen marker, then the human
generation note:

```ts
// @bobsled-inc/sdk-codegen codegen_version=0.20.90 ir_version=1.0
// AUTO-GENERATED by @bobsled-inc/sdk-codegen.
// Do not edit. Regenerate via `dogsled sdk generate --lang ts`.
// IR version: 1.0
// Generated at: 2026-05-12T17:14:00.000Z
```

## Use the Client

The SDK does not open warehouse connections itself. Give it an executor that knows how to query your Dogsled serving tables, API gateway, or MCP bridge.

```ts
import {
  createBobsledClient,
  type EntityFindRequest,
  type BobsledEntityExecutor,
} from './generated/dogsled-sdk/index.js';

const executor: BobsledEntityExecutor = {
  async find(request) {
    return runEntityGraphQuery(request);
  },
};

const dogsled = createBobsledClient(executor);

const result = await dogsled.entity.customer.findBy({ domain: 'acme.com' }).withDocuments().first();
```

The builder methods are:

| Method                    | Effect                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `findBy(filter)`          | Typed per-entity filter shape. Extra keys are a compile error.                                                                        |
| `.withDocuments()`        | Adds `includes.documents = true` on the request.                                                                                      |
| `.withRelationship(name)` | Appends to `includes.relationships`; `name` is a per-entity literal union generated from entity relationships and ontology relations. |
| `.limit(n)`               | Positive integer; rejects 0 / negatives / non-integers at runtime.                                                                    |
| `.all()`                  | Returns `EntityFindResult[]`.                                                                                                         |
| `.first()`                | Returns the first row or `null` (sugar over `.limit(1).all()`).                                                                       |

## The Executor Contract

The single function your app code provides:

```ts
interface BobsledEntityExecutor {
  find<TProfile, TFilter extends object, TDocument = unknown>(
    request: EntityFindRequest<TFilter>
  ): Promise<Array<EntityFindResult<TProfile, TDocument>>>;
}
```

`find` always returns an **array** — `.first()` and `.all()` are SDK-side conveniences over the same call. The array is the natural shape for the `LIMIT n` case; an empty array means "no match."

The request:

```ts
interface EntityFindRequest<TFilter extends object> {
  entity: string; // e.g. 'customer'
  filter: TFilter; // strict per-entity FindFilter shape
  includes: {
    documents: boolean;
    relationships: string[];
  };
  limit?: number;
}
```

The generated TypeScript SDK also exports a runtime allowlist:

```ts
import { RELATIONSHIPS_BY_ENTITY } from './generated/dogsled-sdk/index.js';

RELATIONSHIPS_BY_ENTITY.customer; // readonly ['competes_with', ...]
```

Calling `.withRelationship('unknown')` is a compile-time error for typed callers and a runtime error if an untyped string crosses the executor boundary.

The result:

```ts
interface EntityFindResult<TProfile, TDocument = unknown> {
  profile: TProfile; // typed entity profile + _quality
  documents: TDocument[]; // empty unless includes.documents
  relationships: Record<string, unknown[]>;
}
```

`profile._quality` is always present and conforms to:

```ts
interface EntityQuality {
  confidence: number; // 0–1, from cluster strength
  freshness_age_seconds: number; // wall-clock age of most recent source observation
  source_diversity: number; // distinct contributing source systems
  profile_coverage: number; // populated_attrs / declared_attrs
}
```

## Worked Executor — DuckDB

A practical executor against the local `entity_graph.__entity_profile` and `__document_mentions` tables:

```ts
import type {
  EntityFindRequest,
  EntityFindResult,
  BobsledEntityExecutor,
} from './generated/dogsled-sdk/index.js';

export const duckdbExecutor: BobsledEntityExecutor = {
  async find(request) {
    const filterSql = buildFilterClause(request.filter); // your helper
    const limitSql = request.limit ? `LIMIT ${request.limit}` : '';

    const profiles = await duckdb.query(
      `
      SELECT
        entity_id,
        canonical_name,
        profile_attrs,
        confidence,
        freshness_age_seconds,
        source_diversity,
        profile_coverage
      FROM entity_graph.__entity_profile
      WHERE entity_type = ?
      ${filterSql}
      ${limitSql}
    `,
      [request.entity]
    );

    const results: EntityFindResult<unknown>[] = [];
    for (const row of profiles) {
      const profile = {
        entity_id: row.entity_id,
        ...row.profile_attrs,
        _quality: {
          confidence: row.confidence,
          freshness_age_seconds: row.freshness_age_seconds,
          source_diversity: row.source_diversity,
          profile_coverage: row.profile_coverage,
        },
      };

      const documents = request.includes.documents
        ? await fetchDocumentsForEntity(row.entity_id)
        : [];

      const relationships: Record<string, unknown[]> = {};
      for (const rel of request.includes.relationships) {
        relationships[rel] = await fetchRelationshipRows(row.entity_id, rel);
      }

      results.push({ profile, documents, relationships });
    }
    return results;
  },
};
```

The key disciplines:

1. **Always populate `_quality`** — every consumer relies on it being there.
2. **Honor `request.entity` as the discriminator** for `WHERE entity_type = ?`.
3. **Empty `documents` / `relationships` when not requested** — don't quietly include them.
4. **Filter by ACL** if your executor is behind an MCP boundary; the SDK trusts you.

A copy-and-customize reference implementation lives at
[`examples/entity-resolution-sdk/src/executor.ts`](../../../examples/entity-resolution-sdk/src/executor.ts).
It intentionally stays in the example instead of becoming a published factory so application
owners keep control over SQL runner choice, permission filtering, and serving-table layout.

## Worked Executor — MCP Bridge

If your app already serves an MCP `read_source` surface (see [MCP `read_source`](mcp-read-source.md)), the executor can bridge entity queries through it:

```ts
import { BobsledMcpServer, readSource } from '@bobsled-inc/bobsled-core/mcp';

const server = new BobsledMcpServer();

export const mcpExecutor = (principal): BobsledEntityExecutor => ({
  async find(request) {
    const profileRows = await readSource(
      { server, principal, fetcher: profileFetcher },
      {
        source_table: 'entity_graph.__entity_profile',
        limit: request.limit,
      }
    );
    // Map rows into EntityFindResult[] with documents/relationships
    // populated via additional read_source calls when includes are set.
    return mapProfileRowsToResults(profileRows, request);
  },
});
```

This pattern lets a single MCP-fronted backend serve both the typed SDK (for app code) and raw `read_source` (for agents) — same ACL gate, same citation surface.

## Per-Entity Filter Shapes

Filters are strict — there is no index signature, so unsupported keys are a compile error:

```ts
export interface CustomerFindFilter {
  entity_id?: CustomerId;
  domain?: string | null;
  annual_revenue?: number | null;
}
```

If an entity spec has no profile attributes, the filter shape contains only `entity_id?`. Extra keys are not silently dropped; they are a TS2353 at the call site.

## SDK IR — The Bridge Contract

The codegen reads a Zod-strict IR with `ir_version: '1.0'`:

```json
{
  "ir_version": "1.0",
  "entities": [
    {
      "name": "Customer",
      "primary_key": "entity_id",
      "branded_id_type": "CustomerId",
      "profile_attrs": [
        { "name": "domain", "type": "string", "nullable": false },
        { "name": "annual_revenue", "type": "number", "nullable": true }
      ],
      "quality_columns": [
        "confidence",
        "freshness_age_seconds",
        "source_diversity",
        "profile_coverage"
      ]
    }
  ],
  "relationships": [
    {
      "name": "customer_mentioned_in_document",
      "left_entity": "Customer",
      "right_entity": "Document",
      "cardinality": "one_to_many",
      "join_attrs": [{ "left": "entity_id", "right": "resolved_entity_id" }]
    }
  ],
  "polymorphic_groups": [],
  "dialect_capabilities": {
    "supports_json_path": true,
    "supports_full_text": true,
    "supports_vector": true
  }
}
```

Identifier strings (`name`, `primary_key`, `branded_id_type`, attribute names, join attrs) must match `/^[A-Za-z_][A-Za-z0-9_]*$/` — both JS and Python accept them without quoting, and the regex prevents a malformed inventory from emitting invalid TS or escaping the output tree via names like `../foo`.

Attribute `type` is one of `'string' | 'number' | 'boolean' | 'timestamp' | 'json'`. `timestamp` emits as ISO-8601 strings; `json` emits as `unknown` so callers must narrow.

### Versioning

| Change                                        | Bump  | Consumer effect                                    |
| --------------------------------------------- | ----- | -------------------------------------------------- |
| Add an entity type / attribute / relationship | Minor | Regenerate and commit.                             |
| Rename an attribute / entity                  | Major | Opt-in only; regenerate after downstream is ready. |
| Change a type                                 | Major | Same as rename.                                    |
| Delete an attribute / entity                  | Major | Coordinate downstream migration, then regenerate.  |
| Populate `polymorphic_groups[]`               | Minor | Reserved slot; future v1.x.                        |

`polymorphic_groups[]` is reserved — it is always emitted, always empty in v1.0. A future minor bump can populate it without forcing a major. Adding a discriminator field on existing entity types would be major.

The v1 CLI does not ship a deletion-bypass flag. Treat removals as reviewed major-version changes: update the entity graph specs, regenerate the SDK, and commit the generated diff only after downstream callers are ready.

## Regeneration Discipline

- **Treat the generated tree as build output.** Don't hand-edit. Update entity specs, then regenerate.
- **Commit the diff.** Reviewers see the type-level contract change in the same PR as the spec change.
- **Use `--ir-only` in pre-commit.** Cheap validation that catches most spec breakage before the heavy write step.
- **Pin to the IR major version.** The emitted file headers declare `ir_version=1.0` on the first line — your CI gate should fail on unexpected drift.

## CI Pattern

```bash
dogsled sdk generate --lang ts --out ./generated/dogsled-sdk --json
pnpm exec tsc --noEmit
```

The SDK integration suite validates generated output against the repository's supported TypeScript version. Broader TypeScript-version and Python `pyright` compatibility checks are deferred until the public repository has a dedicated compatibility matrix again.

There's a wall-clock budget on generation: the 10-entity production-shape fixture must complete in **60 seconds** of warm-cache CI runtime. Override with `DOGSLED_SDK_BUDGET_MS` if you run on a slower box; the SDK integration suite gates the unmodified default.

## Distribution

**v1 model:** SDKs are generated **into the consumer repo**. They live alongside your source so you vendor, lint, type-check, and version them like any other code asset. Published packages are out of scope for v1.

`@bobsled-inc/sdk-codegen` is an internal workspace embedded in
`@bobsled-inc/bobsled-core`; it is not published or installed independently.
Repository tooling may import its workspace entrypoints, while external
consumers should use documented Dogsled APIs and CLI commands.

## What's Net-New vs Programmatic API Parity

`@bobsled-inc/sdk-codegen` does not replace the programmatic Python / TypeScript API around Model Spec data products. It complements it:

- **Programmatic API** (existing): typed access to Model Spec data products — tables, models, queries.
- **SDK codegen** (new): typed access to **resolved entities, relationships, and document mentions** — the entity graph.

Both can be used in the same app. The generated SDK calls `findBy(...).withDocuments()`; the programmatic API answers "give me the verified query named `monthly_pipeline_summary`".

## Troubleshooting

| Symptom                                       | Likely cause                                                    | Fix                                                                        |
| --------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `SDK IR validation failed: ...`               | Spec produced an inventory that violates the Zod IR schema.     | Check the field path in the error. Common: identifier with `-` or `.`.     |
| `--lang python is not supported in v1`        | CLI wired for TS only.                                          | Use the Python emitter library export, or pass `--lang ts`.                |
| Generated TS fails `tsc --noEmit` with TS2308 | Older release; `EntityQuality` collided in barrel export.       | Update to the v1 emitter — `_quality.ts` is now imported, not re-exported. |
| Generated TS fails `tsc --noEmit` with TS2344 | Strict `FindFilter` interfaces under an old runtime constraint. | Update to the v1 emitter — `TFilter extends object`, not `Record<...>`.    |
| `Failed to write SDK file '<path>': EACCES`   | Output directory not writable.                                  | Change `--out` or fix permissions.                                         |
