# @bobsled-inc/integrations

This workspace is bundled inside `@bobsled-inc/bobsled-core` and is not published on its own. User documentation is in [`docs/`](../../docs/README.md); this README describes the package for contributors.

Pre-built API integration configs for the `Dogsled` extractor. Each integration contains spec and resource YAML specs ready for use.

## Using an integration

```bash
# List available integrations
dogsled integrations list

# Filter by category
dogsled integrations list --category developer-tools

# View integration details
dogsled integrations show github

# View a specific resource spec
dogsled integrations show github repos

# Scaffold into your project
dogsled integrations init github
dogsled integrations init github --resources repos,issues
```

## Adding an integration

1. Find the OpenAPI spec (or write YAML by hand)
2. Generate specs:
   ```bash
   dogsled extract generate <spec_url> --integration <name> --directory /tmp/staging
   ```
3. Review generated files, resolve all `# REVIEW:` markers
4. Create `meta.yml` with display info and auth setup
5. Move files to `integrations/<name>/`
6. Run `pnpm --filter @bobsled-inc/integrations test` to validate

Or use the `/add-integration` skill to automate this workflow.

## Directory layout

```
integrations/<name>/
├── integration.yml       # Transport config (base URL, auth, retry)
├── meta.yml              # Display metadata (name, category, tags, auth setup)
└── resources/
    ├── <resource>.yml    # Extraction spec for one API endpoint
    └── ...
```

## Quality bar

All integrations must pass CI validation:

- **Schema validation** — integration.yml, meta.yml, and resource YAMLs parse against Zod schemas
- **Structural checks** — required files present, names consistent, no duplicates
- **Quality checks** — no `# REVIEW:` markers, primary keys defined, descriptions present, HTTPS only

## Programmatic API

```typescript
import {
  listIntegrations,
  getIntegration,
  getResources,
  buildQueryCapabilitiesManifest,
  getQuerySpec,
  listQueryResources,
  queryResources,
  searchIntegrations,
} from '@bobsled-inc/integrations';

const integrations = listIntegrations();
const github = getIntegration('github');
const resources = getResources('github');
const queryable = listQueryResources();
const capabilities = buildQueryCapabilitiesManifest();
const githubIssues = getQuerySpec('github', 'issues');
const openIssues = await queryResources.github.issues.list({
  input: { owner: 'bobsled-inc', repo: 'bobsled-core' },
  filter: { state: 'open', updated_at: { $gte: '2026-04-01T00:00:00Z' } },
  limit: 25,
});
const results = searchIntegrations('git');
```

## Query resources

Free Resources that declare a `query:` block are discoverable and callable through this package.
`queryResources.*` is the typed surface for a small set of common Resources.
`queryIntegrationResource(integration, resource, opts)` works for the other Resources in the query
catalog. `filter` uses the MongoDB-compatible DSL. Search-only Resources use the same API through
the `search` option.

Billable Resources are not added to this convenience catalog. A server must load the validated
Integration and Resource from its project, then call `queryResource()` from
`@bobsled-inc/bobsled-core/resources` with an `authorizeBillable` callback. This keeps paid calls,
including Exa web search, blocked until the host app gives explicit approval.

### 1. Discover queryable resources

```typescript
import { getQuerySpec, listQueryResources } from '@bobsled-inc/integrations';

const queryable = listQueryResources();
const stripeProducts = getQuerySpec('stripe', 'products');
const stripePaymentMethods = getQuerySpec('stripe', 'payment_methods');
```

### 2. Use a typed wrapper

```typescript
import { queryResources } from '@bobsled-inc/integrations';

const activeProducts = await queryResources.stripe.products.list({
  filter: {
    active: true,
    created: { $gte: 1711929600 },
  },
  limit: 25,
});
```

### 3. Use the generic helper for discovery-only resources

```typescript
import { queryIntegrationResource } from '@bobsled-inc/integrations';

const cardPaymentMethods = await queryIntegrationResource('stripe', 'payment_methods', {
  filter: {
    customer: 'cus_123',
    type: 'card',
  },
  limit: 25,
});
```

The filter DSL accepts scalars as `$eq` shorthand and currently supports `$eq`, `$contains`, `$gte`, `$lte`, `$ne`, `$lt`, `$gt`, and scalar `$not`.

| Shape                                              | Meaning                                  |
| -------------------------------------------------- | ---------------------------------------- |
| `{ state: 'open' }`                                | `state $eq 'open'`                       |
| `{ state: { eq: 'open' } }`                        | `state $eq 'open'`                       |
| `{ state: { $eq: 'open' } }`                       | `state $eq 'open'`                       |
| `{ name: { $contains: 'ops' } }`                   | `name $contains 'ops'`                   |
| `{ updated_at: { $gte: '2026-04-01T00:00:00Z' } }` | `updated_at $gte '2026-04-01T00:00:00Z'` |
| `{ status: { $ne: 'closed' } }`                    | `status $ne 'closed'`                    |

All filters in the same object are AND-combined. OR, `$in`, nested paths, projection, and operators such as `$regex` are not part of the first release. Search-only resources use the same entry points with `search`, for example `queryResources.jira.searchIssues.list({ search: 'project = FOO' })` or `queryIntegrationResource('jira', 'search_issues', { search: 'project = FOO' })`.

For agent/tool-use preflight, generate the machine-readable capabilities manifest with:

```bash
pnpm --filter @bobsled-inc/integrations render:query-capabilities
```

CI can also run the static enum guard:

```bash
pnpm --filter @bobsled-inc/integrations guard:query-enums
```

The enum guard validates query filter enums against bound provider input enums where those provider enums exist. Provider rejection fixtures are not modeled yet, so the guard reports that fixture gap explicitly.
